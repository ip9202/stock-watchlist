## 2. 주식 데이터 유형별 최적 폴링 인터벌 연구

### 2-1. 업계 표준

| 데이터 유형 | HTS/MTS | 웹 포털 | 대시보드 | 본 프로젝트 권장 |
|------------|---------|---------|---------|-----------------|
| 실시간 주가 | ms | 1-5초 | 5-15초 | **15초** |
| 분봉 차트 | ms | 1-5분 | 1-5분 | **1분** |
| 일봉 차트 | 1-5분 | 5-15분 | 1시간 | **5분** |
| 주/월봉 | 일 단위 | 일 단위 | 12-24시간 | **12시간** |
| 시장 지수 | ms | 1-5초 | 30-60초 | **30초** |
| 환율 | 1-5초 | 1-4시간 | 1시간 | **1시간** |
| 뉴스/공시 | 실시간 | 5-15분 | 15-30분 | **15분** |

### 2-2. 장시간별 차등 인터벌

| 장 상태 | 주가 | 지수 | 분봉 | 일봉 | 환율 |
|---------|------|------|------|------|------|
| 정규장 (09:00-15:30) | 15초 | 30초 | 1분 | 5분 | 1시간 |
| 장전 (08:30-09:00) | 5분 | 5분 | 30분 | 30분 | 1시간 |
| 장후 (15:30-16:00) | 5분 | 5분 | 30분 | 30분 | 1시간 |
| 시간외 (16:00-18:00) | 15분 | 15분 | 1시간 | 1시간 | 4시간 |
| 폐장 (18:00-08:30) | 폴링 중지 | 폴링 중지 | 폴링 중지 | 1시간 | 4시간 |
| 주말/공휴일 | 폴링 중지 | 폴링 중지 | 폴링 중지 | 12시간 | 12시간 |

### 2-3. 키움 API 호출 한도 분석

관심종목 20개 기준:
- 주가 15초 폴링 = 80회/분 (20종목 x 4회)
- 지수 30초 폴링 = 2회/분
- 분봉 1분 폴링 = 20회/분
- **합계: ~102회/분 → 한도 100회/분 초과 위험**

**해결 방안**:
1. 주가 폴링을 30초로 조정 (40회/분)
2. 관심종목을 배치로 분할 (10종목씩 교차 폴링)
3. 서버에서 선 업데이트 → 클라이언트는 서버 캐시만 조회

## 3. 아키텍처 옵션 비교

### 3-1. 옵션 A: 프론트엔드 SWR 폴링 (현재 패턴 강화)

**구조**: 클라이언트에서 SWR refreshInterval로 주기적 fetch → 서버 캐시 활용

**장점**:
- 구현 간단 (SWR 설정만 변경)
- 서버 변경 최소화
- 사용자 없을 때 API 호출 없음

**단점**:
- 콜드 스타트 문제 (첫 요청 느림)
- 브라우저 탭 비활성 시 폴링 지연
- 다중 탭 시 중복 요청

### 3-2. 옵션 B: 서버 사이드 스케줄링 (node-cron)

**구조**: instrumentation.ts에서 node-cron으로 캐시 웜업 → 클라이언트는 항상 캐시 히트

**장점**:
- 콜드 스타트 제거 (항상 따뜻한 캐시)
- API 호출 패턴 제어 가능 (rate limiting 준수)
- 클라이언트 구현 단순화

**단점**:
- 서버 리소스 지속 사용
- 스케줄링 로직 복잡도
- PM2 프로세스 재시작 시 복구 필요

### 3-3. 옵션 C: 하이브리드 (서버 캐시 웜업 + 클라이언트 SWR)

**구조**: 서버는 장중 캐시 웜업, 클라이언트는 SWR로 짧은 인터벌 폴링

**장점**:
- 콜드 스타트 제거
- 실시간 체감 향상
- 장시간 감지 서버에서 통합 처리

**단점**:
- 두 레이어 모두 수정 필요
- 복잡도 증가

### 3-4. 권장: 옵션 A (프론트엔드 SWR 중심) + 점진적 개선

**이유**:
1. 현재 프로젝트 규모 (개인/소수 사용자)에 가장 적합
2. 구현 복잡도 최소
3. 나중에 옵션 B/C로 확장 가능
4. 키움 API 호출 한도 내 안전 운영

## 4. 핵심 설계 결정사항

### 4-1. 폴링 주체: 클라이언트 (SWR)

서버 스케줄링보다 클라이언트 SWR 폴링이 본 프로젝트에 적합:
- 사용자 없을 때 불필요한 API 호출 방지
- 구현 단순성
- Next.js standalone + PM2 환경에 적합

### 4-2. 장시간 감지: 공통 유틸

`src/lib/market-hours.ts` 신규 생성:
- `getMarketState()`: 'pre-market' | 'open' | 'post-market' | 'closed'
- 주말 감지 (getDay())
- 장시간 기반 동적 인터벌 반환

### 4-3. 캐시 정책: 서버 TTL을 클라이언트 인터벌 이하로 유지

서버 캐시 TTL ≤ 클라이언트 폴링 인터벌 (그렇지 않으면 캐시 히트로 실제 갱신 안 됨)

현재 서버 TTL:
- 주가 30초 vs 권장 클라이언트 15초 → **서버 TTL을 15초로 단축 필요**
- 지수 60초 vs 권장 클라이언트 30초 → **서버 TTL을 30초로 단축 필요**

### 4-4. 배치 요청: API 호출 최적화

관심종목 N개를 한 번에 조회하는 키움 API TR (ka10099) 활용:
- 개별 조회: N회 API 호출
- 일괄 조회: 1회 API 호출
- 폴링 시 배치 조회로 API 호출 횟수 대폭 감소
